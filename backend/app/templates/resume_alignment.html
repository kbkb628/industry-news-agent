Resume Alignment

This page translates the implemented monitor runtime into concise, recruiter-readable language. It is meant to help position the project as a backend system with visible orchestration, reliability concerns, and product-facing outcomes.

Adapter code alone does not imply a live service or enabled provider in the target runtime.

Interview talking points
  • Built a FastAPI-based monitor loop that turns topic context into actionable push decisions.
  • Used LangGraph for top-level supervision, with candidate-level fetch, extract, and evaluate task orchestration inside the run.
  • Exposed structured stage contracts, candidate task evidence, trace events, push records, evaluation signals, and optional adapter runtime evidence through APIs and readable pages.
Suggested resume framing
  • Emphasize supervisor-driven multi-agent orchestration plus candidate-level task scheduling.
  • Use structured stage contracts as the primary explanation of how planner, retrieval, extraction, and evaluation outputs move through the run.
  • Explain MCP/search/browser/notification integration as one unified tool-access contract with visible per-capability provider paths and gateway-stamped per-call access evidence.
  • Describe fallbacks, task ledger evidence, per-run configuration/usage/degradation evidence, and quality metrics as signs of resilience-minded engineering.
  • Describe reliability as bounded concurrency, retry, timeout, and active-run controls rather than as a distributed worker fleet or full circuit-breaker system.
  • Use this page as a bridge between runtime truth, interview wording, and demo order.
Truth boundary
  • The top-level graph is `Supervisor -> Planner -> Retrieval -> CandidateTaskOrchestrator -> Finalize`.
  • LangGraph uses structured stage contracts for `planner_output`, `retrieval_output`, `extraction_output`, and `evaluation_output`, while legacy mirrors stay available for compatibility.
  • Fetch, extract, and evaluate still exist as real specialist behaviors, but they run under the candidate task orchestrator instead of as top-level graph nodes.
  • The run snapshot separates `integration_runtime.tool_access.contract` from per-capability `provider_path`, so unified access does not over-claim universal MCP execution.
  • The same snapshot now also exposes gateway-stamped per-call access evidence, so unified access is backed by real run-level call records rather than only by settings-time inference or display-layer summaries.
  • Optional MCP and browser adapters can produce real per-run configuration/usage/degradation evidence when the target runtime wires them, but they remain optional and are not guaranteed always-live deployments.
  • Judge and history-index adapters still remain runtime boundaries unless the environment explicitly enables them.
  • Worker governance and candidate-task coordination are real, but they are still single-process and bounded rather than a distributed worker fleet.
Suggested demo order
  • Open the dashboard or topic page to establish monitoring scope.
  • Show run detail, RAG grounding evidence, and candidate task readback to explain structured stage contracts plus bounded same-stage orchestration.
  • Finish with trace events, pushes, and quality metrics to show reliability and evaluation evidence.
RAG grounding evidence
  • The local knowledge-base retrieval result is persisted under business_context and mirrored into business_memory.business_context.
  • semantic_memory gives planner and evaluation a stable contract for topic keywords, trusted-source hints, source preferences, push rules, and history guidance.
  • Run detail surfaces can show both the retrieved semantic guidance and the resulting RAG-impact metrics such as guidance hits and trusted-source matches.
Truthful wording
  • Describe this as local structured RAG grounding, not as an external vector database deployment.
  • Emphasize that planner and scoring behavior are measurably influenced by retrieved business guidance.
  • Use the run-level read surface to prove the effect chain instead of treating RAG as background implementation detail.

MCP runtime

Treat this section as runtime evidence, not a promise that a live MCP deployment always exists: some environments intentionally stay on the local gateway path, and some runs may show no MCP usage at all. In this repo, MCP evidence should be read alongside the unified tool-access contract so "tool is reachable through one contract" is not confused with "tool actually ran through MCP in this run."

Tool access contract

integration_runtime.tool_access separates the stable access contract from the actual provider path. contract shows that search, browser, and notification are read back through one unified tool surface, while each provider_path shows whether the run stayed on the local tool gateway or crossed an MCP-backed boundary.

Browser fallback runtime

Browser fallback runtime explains whether candidate fetching escalated beyond normal HTTP reads. When Playwright-backed browser fetch is wired, the run can preserve evidence about allowed-domain gating, actual fallback usage, fallback reason, and degraded browser attempts.

This remains optional by design. A truthful run may show pure HTTP fetching with no browser escalation, or it may show fallback evidence only for the specific candidates that needed it.

Notification runtime

Notification runtime explains whether persisted push records also crossed the optional delivery boundary in this run. It should be read as per-run delivery evidence, not as a claim of a production notification queue or guaranteed downstream delivery.
